## Post-delivery enhancement 6: automatic plan interpretation

The import pipeline now performs the full semantic interpretation itself:

1. **Wall accuracy** — noise-speck removal (small floating components) plus
   binarize-before-downsample thin-line preservation (from earlier).
2. **Door detection** — run-based scans along rows/columns find gaps in wall
   lines; each candidate is verified by a per-group connectivity flood test
   (removing the gap must actually separate the plan) and a wall-continuation
   check (the pierced wall must continue beyond the gap — rejects
   room-interior slices). Consecutive candidate stacks (narrow corridor
   cross-sections) are filtered.
3. **Automatic exits** — openings leading off the plan become exits with
   width-based capacities (width_m × 1.3 p/s/m).
4. **Automatic zones + populations** — flood-fill room segmentation
   (interior regions ≥ 6 cells, ≤ 15 zones); suggested population = area ×
   occupancy density (user parameter, default 0.25 persons/m²).
5. **One-click flow** — the import page reports rooms/doors/exits/zones and
   offers "Convert & run evacuation": creates the building (with detected
   exits/zones), the suggested scenario (dt rounded DOWN to satisfy the
   engine's dt bound), and starts the run — verified end-to-end: bundled
   sample plan → 3 exits, 5 zones, populations 28/26/14/14/2 → run #7
   completed 82/84 evacuated in 36.1 s (2 occupants in an unreachable margin
   region, honestly reported with warnings).
6. Editor draft adoption now includes the auto-detected exits/zones.

## Post-delivery enhancement 8: exterior-ring exit fix

User report: exits were not being marked for uploaded plans. Root cause: the
exit classifier required a candidate opening to lead OUT OF BOUNDS, but
auto-crop insets the plan with a 2-cell pad — a door to the outside leads to
the floor MARGIN ring, not off-grid, so exterior doors were misclassified as
interior doors and no exits were placed. Fixes:

1. **Exterior flood region** — computed once per plan: the floor cells
   reachable from the image border with all candidate gaps removed (the
   margin ring around the envelope).
2. **Exit rule** — an opening with exactly one side in the exterior flood is
   an exit; both sides → outside passage (ignored); neither → interior door
   by the separation flood test.
3. **Margin candidates rejected** — floor runs flanked by the grid edge
   (outside the envelope) are not door gaps; flanking walls must be real
   in-bounds cells.
4. **Zone exterior rule simplified** — regions containing exterior-flood
   cells are the outside; heuristics (largest-region, margin-band) removed.

Regression test added: envelope inset from the grid edge with a margin ring
→ exit detected through the ring. Verified live: sample plan → 3 exits →
one-click run marks all 3 in the simulation's exit-utilization table.
Tests: **122 backend**, lint clean.

## Post-delivery enhancement 9: draw.io import + recognition fixes

User report: "the system is not able to recognize the uploaded image". Three
root causes found and fixed, plus the draw.io feature:

1. **draw.io import (precise vector conversion)** — `.drawio` / `.xml` files
   parsed as mxGraph XML (including draw.io's compressed diagram payload:
   base64 → raw-deflate → URI-decode). Filled shapes → solid walls,
   unfilled shapes and edge lines → wall outlines rasterized with
   Bresenham at exact grid positions, text labels skipped. The semantics
   pipeline (doors/exits/zones/populations) runs on the vector-true walls.
   Edge parsing ignores shape references and relative geometry x/y (both
   would corrupt coordinates). Sample `sample-plan.drawio` added with
   envelope door gaps; 9 tests including a full pipeline
   (draw.io → building → scenario → completed run).
2. **Inverted-plan crop polarity bug** — the content bounding box was always
   computed from the inverted binary, so for light-on-dark plans the crop
   chopped OFF the walls (the ink is the bright class there). Polarity now
   follows the invert flag. This was a core "image not recognized" cause.
3. **Draft/semantics consistency** — noise-speck removal happened inside the
   semantics but the draft kept the original walls, so zone cells could
   contain wall cells ("Zone ZA contains a wall cell" on save). Importers
   now adopt the semantics' cleaned wall set.
4. **Crop pad removed** — the 2px pad thinned the outermost wall line below
   the density threshold; the exterior-flood exit detection no longer needs
   a pad ring.

Also fixed en route: draw.io edge geometry x/y is a layout hint (not a
coordinate) and targetPoint was double-appended; the suggested-scenario dt
now rounds DOWN to satisfy the dt ≤ cell/max-speed validation.

## Post-delivery enhancement 11: disaster scenarios (fire / earthquake / stampede)

User request: "add different scenarios like earthquake, fire, stampede... and
in those scenario how the evacuation plan held on" + "a section where you
include under what basis the system creates the simulation."

1. **Disaster models** (`app/simulation/disasters.py`) — three dynamic
   processes that evolve during the simulation, blocking cells and forcing
   re-routing:
   - **Fire**: ignites farthest from exits, radius grows at
     (0.05 + 0.20 × intensity) cells/s; occupants on newly burning cells are
     incapacitated; smoke permeates walls (no CFD).
   - **Earthquake**: collapses at t = 30 − 20 × intensity; debris blocks
     round(intensity² × 0.12 × floor) cells near exits first; occupants on
     debris are crushed; waiting occupants' reaction times extended by
     25 × intensity (confusion).
   - **Stampede**: congestion-triggered crush zones (8 s window, intensity-
     dependent threshold) become impassable obstacles (fallen people);
     occupants are shoved to free neighbors.
2. **Engine integration** — dynamic blocked cells overlay the static walls;
   exit distance fields recompute when the network changes; all occupants
   re-route to the nearest reachable exit; incapacitated is a terminal status
   in the mass balance: total = evacuated + unreachable + incapacitated +
   remaining.
3. **UI** — Scenario Editor "Disaster scenario" card (type select + intensity
   slider + model description); Run page disaster summary banner +
   Incapacitated timeline line + status legend entry; **Methodology page**
   documenting the full simulation basis, routing strategies, disaster
   models with formulas, mass balance, and limitations.
4. **Samples** — "Fire (severe)" and "Earthquake (moderate)" sample
   scenarios; fire verified live: 99/120 evacuated, 21 incapacitated, 214
   cells burned.
